# 44 — FFT Helper Cluster `0x00e83010 / 0x00e83530 / 0x015c4d90`

**Ultimo aggiornamento:** 2026-04-09

## Obiettivo

Ridurre il front-end FFT condiviso a primitive piu' concrete:

- allocator / release helper
- wrapper forward FFT
- companion inverse-like
- adapter sopra `MUSpectralTimeSlice::initFromTimeSignal`

---

## Conclusione Principale

Il cluster oggi si puo' leggere cosi':

1. `0x00e83010` — thin allocation helper
2. `0x00e83020` — alloc + zero helper
3. `0x00e83070` — safe release helper
4. `0x00e83530` — `GNFastFourierTransformer` forward real FFT wrapper
5. `0x00e83640` — inverse-like companion sullo stesso transformer
6. `0x015c4d90` — thin adapter / ownership wrapper sopra `0x015c4e40`

La parte importante per la replica e' questa:

- `0x00e83530` non e' piu' solo un generico "execution stage"
- e' una primitive concreta che incapsula `vDSP_ctoz -> vDSP_vsmul -> vDSP_fft_zrip -> vDSP_vsmul -> vDSP_ztoc`

## 2. `0x00e83530` Come Wrapper Forward FFT Reale

La disassembly di [binaries/MikeCore](/Users/michaelbelmonte/Desktop/Progetto_Reverse_Mike/binaries/MikeCore) a `0x00e83530` mostra una sequenza stabile:

1. `callq 0x1f9b67c` = `_vDSP_ctoz`
2. `callq 0x1f9b6b2` = `_vDSP_vsmul`
3. `callq 0x1f9b6b2` = `_vDSP_vsmul`
4. `callq 0x1f9b688` = `_vDSP_fft_zrip`
5. `callq 0x1f9b6b2` = `_vDSP_vsmul`
6. `callq 0x1f9b6b8` = `_vDSP_ztoc`

Binding import verificato con:

- `otool -Iv binaries/MikeCore`

Mapping:

- `0x1f9b67c` → `_vDSP_ctoz`
- `0x1f9b688` → `_vDSP_fft_zrip`
- `0x1f9b6b2` → `_vDSP_vsmul`
- `0x1f9b6b8` → `_vDSP_ztoc`

Dettagli osservabili:

- usa `self + 0x18` e `self + 0x20` come split-complex buffers
- usa `self + 0x28` come `fftsetup`
- usa `self + 0x10` come count di bin/half-size
- usa `self + 0x14` come `log2(size)` per `vDSP_fft_zrip`
- costruisce uno scale `1 / self[0xc]`
- applica una normalizzazione con `vDSP_vsmul` prima della FFT
- applica una correzione di segno a `-1.0f` su un lane/buffer dopo `fft_zrip`
- ricompone l'output con `vDSP_ztoc`

Lettura operativa prudente:

- wrapper forward real-to-packed-spectrum del transformer
- il dettaglio esatto della sign correction post-FFT resta secondario ma reale

Nome di lavoro consigliato:

- `GNFastFourierTransformer_forwardRealSignalToPackedSpectrum`

## 3. `0x00e83640` Come Companion Inverse-Like

La funzione adiacente `0x00e83640` mostra:

1. `_vDSP_ctoz`
2. `_vDSP_vsmul` con `-1.0f`
3. `_vDSP_fft_zrip` con direction `-1`
4. `_vDSP_vsmul` con `-0.5f` sul primo split buffer
5. `_vDSP_vsmul` con `-0.5f` sul secondo split buffer
6. `_vDSP_ztoc`

Questo pattern e' fortemente coerente con:

- companion inverse / packed-spectrum-to-time-domain wrapper

Confidence:

- media-alta sul verso inverse
- molto alta sul fatto che sia il sibling operativo di `0x00e83530`

## 5. `0x015c4d90` Come Adapter Thin Sopra `015c4e40`

La disassembly di `0x015c4d90` mostra che la funzione:

- materializza su stack piu' wrapper `ptr + ownership flag`
- azzera i flag locali
- inoltra tutto a `0x015c4e40`
- non implementa calcolo spettrale autonomo

Il pattern corrisponde bene a:

- adapter/thunk con normalizzazione degli ownership wrapper
- layer sottile sopra `MUSpectralTimeSlice::initFromTimeSignal`

Quindi `0x015c4d90` non va trattata come factory FFT e nemmeno come kernel DSP.

Nome di lavoro consigliato:

- `MUSpectralTimeSlice_initFromTimeSignal_adapter`

## 6. Nota Sulle False Return Values

In diversi decompilati `0x00e83530` e `0x00e83640` sembrano "ritornare" un valore poi riassegnato.

Lettura prudente:

- questo e' molto probabilmente rumore da prototype mancante nel decompilatore
- non c'e' evidenza forte che il semantic return sia parte importante del contratto

Per la replica clean-room conviene trattarle come:

- primitive operative con effetti sui buffer
- non come funzioni che producono un valore numerico significativo
